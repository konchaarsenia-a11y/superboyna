| | LEGACY (старые) | RAW26 (новые с **2026-08-31**) |
|--|--|--|
| Формула | `сырьё×coef + 11 + 6×N + пакеты` | `сырьё×M + recover + 9×N + пакеты + фракции`, затем `min(полная, capBase×0.92)`; capBase = R≥80 ? R : R+9×N |
| M / coef по умолч. | 2.3 | **2.6** |

| Календарь доставок | без изменений | без изменений (migrate тоже не трогает) |

Ручной перевод старого ПП: кнопка в карточке → action `migratePpToRaw26Scheme`.

**Оффер / сообщение клиенту (2026-09-15):** RAW26 шлёт **fact**, не завышенный stated. LEGACY — указанная.

**Крошка-миксер в RAW26 (канон 15/17/20):** кнопка «Крошки» — не фракция позиции. В сырьё ПП идёт `(г/100)×ставка`: овощи/фрукты **15**, мясные **17**, гипоаллергенные **20**. Дальше обычная RAW26 (`×M + recover + 9×N + пакеты + фракции`, кап). Нарезка разворачивает крошку в исходные позиции по `sources`/`ratio`. Фракция «Крошка» у SKU (не миксер) — в родителе, не в matcher наценок. Ставки миксера не меняли, когда крутили наценки фракций. Подробно: [FRACTION-MARKUP-CANON.md](./FRACTION-MARKUP-CANON.md).

**Указанная vs факт (2026-09-19):** refresh мини-аппа не переписывает `statedCost`. Внос заказа ПП подставляет цену с листа (указанная), не свежий calc.

**Финальный кап (2026-09-20, правило Арсения):** розница **от 80 BYN — доставка бесплатна**, поэтому `9×N` в базу сравнения кладём только если товарная розница ниже порога.

```
R = Σрозница_строк_состава   # крошка = розница source SKU (#335)
capBase = R >= 80 ? R : R + 9×N
цена = min(полная RAW26, capBase × 0.92)
```

В базу капа **не** входят пакеты и наценки фракций. Если Σрозница строк = 0 / нет прайса — кап не применять, цену не выдумывать.

rit_murr live: retail calc **171.20** (крошка-миксер veg 15, как вкладка Розница) ≥ 80 → cap = 0.92×171.20 = **157.50**.
#335/хаб 166.20 брали крошку как source РУБЕЦ Т=10 — это не то R, что видит розничный калькулятор (разрыв −5). Не 161.18 (всегда +9) и не 152.90.
dasha_2135: R=55 < 80, N=2 → base 55+18=73, кап **67.16**.

Если черновик выше капа — **не** масштабировать всё. Excess режем так:
1. сначала наценку фракций до 0;
2. если мало — товар (`сырьё×M+recover`) до пола `сырьё+recover`;
3. пакеты — только после этого пола;
4. доставку 9×N и товар ниже пола — **только если иначе цена > капа**.
Итог convert/calc всегда `≤ retailCapBase×0.92` (крошка в базе = розница source SKU).

dasha2135: полная ~75, кап 67.16 → фракции 11→3.16; товар/доставка/пакеты как были.

**Чистые оффера RAW26** (не путать с месячным `getStats` при нарезчике OFF):  
`чистые = цена − сырьё − recover − пакеты − 4×N` (топливо как в `STATS_DELIVERY_FUEL_PER_`). Фракции и остаток доставки 5×N остаются в чистом. API: `cleanBeforeCap` / `cleanAfterCap` + `factBeforeCap` / `factAfterCap`. В Расчёте и карточке ПП всегда оба числа: «Чистыми до капа» / «Чистыми после капа» (если кап не сработал — одинаковые).

Подробный разбор (сырьё, recover, товар до капа, фракции до/после, пакеты, 9×N, база капа, цены, чистые, что срезал кап) — кнопка «Экономика». Только **owner/all и верный PIN** из `PP_COST_BREAKDOWN_PIN` (Script Property + Worker secret; значение у хаба, не в git; см. `DEPLOY.md`). Пустой секрет → панель закрыта. Курьер/нарезчик не видят.

Первый кап дня резал полную цену по `Σрозница×0.92` **без** доставки → ПП с `9×N` проседала ниже товарной розницы (dasha_2135: товар 55, N=2 → было 50.60, надо 67.16). Теперь база 55+18=73, кап 67.16. LEGACY не трогаем.

## 0. Философия

1. **Зарабатывать только на сырье** — накрутка `M` только на `Σ(сырьё)`.
2. **Свет / нарезка / дойпак** — в цену **по себесу** (×1), без прибыли.
3. **Жевалки шт** — в сушилке почти не занимают место, режутся быстро → recover **мягкий** (`+0,50`), не `+2,40`.
4. **Полная цена ПП < розницы, с которой сравнивает клиент** — потолок 92% от `capBase`: если R≥80 розница без доставки, иначе R+9×N. Пакеты и фракции **не** в базе капа, но входят в полную цену ПП и поэтому могут упереться в потолок.
5. Пакеты/крафт УП4 — в формуле без наценки, но не выводят итог выше капа.

Раньше (ошибочно для твоей логики): накрутка на полный COGS → ты ещё «зарабатывал» 35% на свете и ЗП.

## 1. Формула новых ПП

```
recover_100г = 3,90          # свет+нарезка+дойпак — только возмещение
recover_шт   = 0,50          # жевалка: доля пака + чуть труда (не 2,40)

товар = Σ(сырьё)×M + Σ(recover)
фулфилмент = 9×N + пакеты + фракции
черновик = товар + фулфилмент
capBase = R>=80 ? R : R+9×N              # пакеты и фракции не в базе; от 80 доставка розницы бесплатна
цена = min(черновик, capBase×0,92)       # нет розницы строк → черновик как есть
# кап: excess с фракций → товар до сырьё+recover → пакеты; 9×N/пол — если иначе > капа

вклад = Σ(сырьё)×(M−1) + (9−7)×N   # до капа; если кап сработал — вклад меньше
# recover и пакеты в нуле; с доставки +2 за шт доставки
```

| Параметр | Значение |
|----------|----------|
| **M на сырьё** | **2.60** база для новых (RAW26) |
| recover 100г | **3.90** |
| recover жевалка шт | **0.50** |
| F | **9** × N |
| Пакеты | pass-through |
| Старые ПП | без изменений `×2,3 + 11 + 6×N + пакеты` до ручного migrate |

### Жевалки

Старое `+2,40` на шт размазывало ЗП/свет как на 100г дрессуры — **криво** для корня/трахеи/уха.
Рабочая норма **0,50** (пак ~0,40 + чуть рук). Если по факту цеха мало — можно **0,30–0,40**.

## 4. Вердикт

- База новых: **M=2.60 только на сырьё**, recover 100г=3.9, жевалка=0.5.
- Полная цена RAW26 ≤ 92% от capBase (R≥80 → только Σ розницы; R<80 → Σ+9×N). Иначе ПП не имеет смысла против той розницы, которую клиент реально платит.
- Вклад ≈ `сырьё×(M−1) + 2×N` до капа; кап сжимает вклад, не розницу.
- Старые карточки и уже внесённые доставки не пересчитываются; перевод — вручную.
- Жевалки: не раздувать recover — иначе цена растёт без роста заработка на сырье.
